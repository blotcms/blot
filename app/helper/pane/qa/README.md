# pane QA

Compares what `pane` renders with the real OS screenshots in `../reference/`
(Finder, File Explorer, GNOME Files; light and dark; every captured view), so a
change to the CSS can be judged by metrics as well as by eye.

    reference/   real screenshots captured on CI (read-only; regenerated by pane-screenshots)
    rendered/    pane's rendering of the same case, one PNG per reference, same file name
    qa/          this tooling; qa/out/ (git-ignored) holds diff images and reports

## Commands

```sh
node app/helper/pane/qa/render.js [--os macos] [--case ID]   # render cases into rendered/
node app/helper/pane/qa/diff.js [--case ID] [--os X] [--theme X] [--view X] [--json] [--explain]
node app/helper/pane/qa                                      # viewer on http://127.0.0.1:4173
```

The unit tests (`qa/tests/`) are pure and fast; they run with the repo's test
runner like any other (`npm test app/helper/pane/qa`), but CI is the place to run them.

## Cases

Every image in `reference/<os>/` is a case, found by scanning the directory, so new
screenshots appear automatically. The ID is `<os>-<theme>[-<view>]` (the default view
has no suffix): `macos-dark`, `macos-dark-icons`, `windows-light-tiles`,
`linux-light-sidebar`. See `lib/cases.js` for what each case records: scale, image and
logical size, padding, **masks** and **regions**.

- **Masks** are excluded from every metric. The date column is masked in every view that
  has one, because the OS prints time-dependent text ("Today at 3:38 PM", `9/20/2026
  3:37 PM`, "Today 15:38"), which also covers the "today"-relative rows. Override per
  case in `qa/masks.json` (`{ "<id>": [{ "name", "x", "y", "w", "h" }] }`, CSS px from the
  window's top-left; `right`/`bottom` measure from the other edges, `w`/`h` `null` run to
  the edge).
- **Regions** split the window so chrome (title bar, toolbars, status bar) can be held to
  a stricter limit than text. Glyphs never match pixel for pixel across renderers, so
  text is also compared by **row positions**: where the lines of text sit, not what they look like.
- Only the window is compared. Each image is cropped to the window rectangle it
  detects itself (the non-`#808080` bounding box; a soft shadow is a gradient, the
  window edge a hard step, so the shadow is not mistaken for window), which aligns the two
  without depending on the padding. The desktop around it is used for the **shadow profile**.

### Metrics

The raw diff % is diluted by large flat areas, so regions also get:

- **ink %**: differing pixels / pixels that are ink (differ from the region's dominant
  colour) in either image. This is the number that moves as glyphs and icons improve.
- **flat colour** (deltaE, CIE76): the dominant colour of each region against the
  rendering's, with a hint such as `titlebar background should be #ececec (rendered
  #f6f6f6)`. Wrong greys are the most common CSS error; deltaE above ~2 is visible.
- **blurred error**: mean absolute error after a small blur, as % of full scale. It forgives
  anti-aliasing and 1px shifts, not wrong colours or missing elements.

A test (`tests/masks.js`) checks that every mask holds text and does not cut through it,
so a regenerated reference that moves a column fails loudly instead of skewing the
numbers. Update the mask in `lib/cases.js` when it does.

### Things that are true of the references

- Finder's minimum width is about 484px, Explorer's about 386px; all windows are
  nominally 490px wide, and the detected sizes (491x361 Finder, 504x367 Explorer, 490x520
  GNOME Files) are what to build to. The renderer places the window where the reference
  has it.
- Explorer shows extension-less names ("About", not "About.txt") and absolute dates.
- The Linux capture draws its rounded corners synthetically and has **no shadow**. The
  Windows capture has none either (the DWM shadow is not in the capture). Their
  reference shadow profile is flat, so the shadow error for them measures how much
  shadow the rendering adds: it should add none.
- Windows 2x is only 360px tall.

## The adapter

`adapter.js` defines `render(caseId) -> { html, css } | null`. The real `pane` module
plugs in by pointing `PANE_QA_ADAPTER` at a module exporting `render(caseId, caseDef)`
(returning `null` falls through to the fixtures). Until then, hand-written pages in
`fixtures/` are used:

    fixtures/<caseId>.html        one exact case
    fixtures/<os>-<view>.html     both themes; style the dark theme with
                                  @media (prefers-color-scheme: dark)

A fixture is a fragment (markup plus an inline `<style>`) for the window only. The renderer
puts it on the `#808080` desktop where the reference's window is, sets
`prefers-color-scheme` to the case's theme, sets `<html data-os data-theme>`, and freezes
`Date` to `2026-09-20T15:38:00`. Fixtures should hard-code any dates they show. The
three shipped fixtures are crude on purpose: they make the tooling usable and testable.

## Rendering, fonts and CI

`render.js` uses Puppeteer at `deviceScaleFactor` = the reference's scale, with the
viewport = reference size / scale. Fonts come from the machine, so the **pane-qa**
workflow renders each OS's cases on the matching runner (macOS, Windows, Ubuntu with
`fonts-cantarell`) and commits `rendered/<os>/`, like pane-screenshots does for
`reference/`. Rendering locally works too; render only the OS you are on (`--os macos`),
because Segoe UI Variable and SF will not exist on the wrong machine.

## For agents: the loop

```sh
# 1. edit the CSS/HTML (or the fixture)
node app/helper/pane/qa/render.js --case macos-light
node app/helper/pane/qa/diff.js --case macos-light --explain
# 2. repeat until it passes
```

`--explain` prints failing metrics, the shadow error and the largest diff clusters with
their coordinates in **CSS px from the window's top-left**, e.g.
`#2 at 48,265 107x18 in content`, so you know exactly where to look. Look at the
images in `qa/out/<id>/` (`reference.png`, `rendered.png`, `diff.png`, `heatmap.png`,
all aligned and the same size, with a 24px margin of desktop; pixels are 2x) when
coordinates are not enough. Change one thing at a time and re-run: chrome (title bar,
toolbars, borders, icons) has the strict limit, so fix it first.

`--json` prints the report to stdout (also saved to `qa/out/report.json`): stable
keys, numbers rounded to 3 places, no timestamps. Per case: `status`
(`pass`/`fail`/`missing`/`error`), `failures`, `diff`, per-`regions` percentages, text
`rows`, `shadow` (error, per-edge error and both curves), `geometry`, `masks` and
`clusters` (ranked by area). Exit status is 0 when everything passes, 1 on failures or
missing renders, 2 on errors.

Limits are in `thresholds.json` (`default`, overridden per case in `cases`): the % of
compared pixels that differ overall and per region name or kind, shadow RMSE (luminance
levels), window size difference (CSS px) and text row offset (CSS px). They start loose;
tighten them as the rendering improves, per case when one view lags.

## Viewer

`node app/helper/pane/qa [--port N]` serves it on 127.0.0.1. The case list filters by OS,
theme, view and result; modes are side by side (reference | rendered | diff), swipe,
onion skin, blink and live HTML (the case in an iframe, resizable, next to the reference). Zoom (to 400%, crisp pixels)
and pan are shared between the panes; the pixel readout shows both images' colours
under the pointer; the diff pane can show the heatmap; masks and diff clusters can be
overlaid; the shadow chart shows the four edge curves. It reloads when rendered images, fixtures,
thresholds or references change, and can re-render the current case (optionally
whenever the fixture changes). Keys: `j`/`k` cases, `1`-`5` modes, `h` diff/heatmap, `m`
masks, `c` clusters, `[` `]` cluster, `b` blink, `+` `-` `0` zoom, `r` re-render, `?` help.

## The module skeleton and its contract

`../index.js` is a very basic first cut of the real module: `pane.render(text, { title })`
returns `{ html, css, js }` (a figure per window, one shared stylesheet skinned by
`html[data-os]`, and a tiny head snippet that sets `data-os`). `pane-adapter.js` plugs it
into the harness for the default view of every OS/theme; other views fall back to
`fixtures/`. Set `PANE_QA_FIXTURES=1` to use only the fixtures.

The adapter passes the module the **view** (`list` for the default view, then `icons`,
`columns`, `gallery`, `tiles`, `content`, `sidebar`); the module returns `null` for views
it doesn't implement (`SUPPORTED_VIEWS`), and add a view there to have the harness render
it instead of the fixture. It also passes the **sample data** in `sample.json` (true
byte sizes and frozen modified times of the "Your site" folder) as `files`, with `now`.
Per-OS formatting ("6 bytes" / "2.7 kB", "3:38 PM" / "Today 15:38" / `9/20/2026 3:38 PM`)
is module logic, tested in `../tests/index.js`.

## Checks

`node app/helper/pane/qa/smoke.js` starts the viewer in Chrome and checks the case list,
the images and the console. The workflow runs it. The renderer logs which font Chrome
really used per case (`fonts: .SF NS (684)`), so a silent fallback (Arimo instead of
Segoe UI Variable) is visible in the log, and one failing case no longer stops the rest.
