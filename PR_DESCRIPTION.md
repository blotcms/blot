PR 6 of #2119: the Deploy workflow deploys the two units, `blot-blue` then `blot-green` (OpenResty, node-a and node-b in one container from `blot-unit:<sha>`), and the first run is the cutover from today's proxy-only containers and the `blot-container-*` Node containers. Based on master, which now has the unit image (#2248).

**One deploy script.** `proxy/deploy/blue-green.sh` and `common.sh` deploy either kind of image, decided by the image's name (`blot-unit` is a unit, anything else is a proxy alone, `PROXY_DEPLOY_KIND` overrides). The flow, ordering, refusal rules, skip-if-same-image, `-previous` rollback and exact-name matching are unchanged. A unit also gets: both env files (`/etc/blot/secrets.env`, then `proxy.env`, then `-e` settings; a key the two files set to different values is refused before anything is touched), `BLOT_UNIT`, `BLOT_SOCKET`/`BLOT_WORKER_SOCKET`, `BLOT_RELEASE_ID`, the data directory with `rslave`, the tmp directory, `/run/blot`, `--stop-timeout`, a memory/cpu/shares budget, `NODE_OPTIONS` for node-a (heap and crash report) and `BLOT_WORKER_MAX_OLD_SPACE_SIZE` for node-b. Health is the proxy's socket plus node-a and node-b `/health` on their sockets, judged per container (so a proxy-only peer counts as healthy during the cutover). Blue also runs `scripts/deploy/verify-container` before green is touched. `units.sh` (was `proxy.sh`) writes the numbers from `scripts/deploy/constants.js` (new `UNIT`, `AIRLOCK.units`) to `unit-settings.env` beside the scripts on every run, so they live in one place. Per unit: 4 cpus, 3840m, shares 2048, node-a heap 1800 (yellow's 1500 plus room for blue's dashboard reads), node-b heap 750 (green's); one unit has to carry everything while the other is replaced, so each is sized for what the three containers did together.

**Cutover.** From proxy-only `blot-blue`/`blot-green`: blue becomes a unit (green still routes to the old Node containers, which the checks keep requiring while it does; the new blue's backups do not exist yet, which is fine), then green; only when both are healthy units and the checks pass are the old Node containers and `blot-airlock` stopped with `docker stop --time 30` (not removed). If stopping fails they are started again. Every step is idempotent, so a run that is cut off is simply run again. The rollback (start the old containers, deploy the proxy-only image with `units.sh --proxy-only`) is in `proxy/deploy/README.md`.

**TCP port.** On the host network two units would both bind 8080, and 8088-8090 are held by the old containers during the cutover. Nothing in a unit needs the port: the proxy, the image's HEALTHCHECK, the deploy and `verify-container` use the sockets (the only other user of `config.port` is the development-only webhook relay). With `BLOT_UNIT` set and no `BLOT_PORT`, node-a now serves on its socket alone; `verify-container` talks to the socket. The old containers are unaffected.

**Airlock.** A host-network container cannot join `blotnet` or resolve `blot-airlock`, so each unit has its own airlock, `blot-<unit>-airlock`, replaced just before the unit (while it is stopped) and published on `127.0.0.1` only (19222/18888 for blue, 19223/18889 for green); the unit gets `BLOT_AIRLOCK_*_URL` for its own. The egress filter is in the airlock's own network namespace and rejects by the real destination of each connection, so it does not depend on how its clients reach it, and tinyproxy's ACL already allows the bridge gateway address a published port presents. What weakens is who may use it: anything on the host's loopback can now reach the unauthenticated DevTools and proxy ports, where before only containers on `blotnet` could. I think that is acceptable (the host's loopback already holds the purge and health listeners, and the airlock still only reaches public addresses) and said so in `config/airlock/README.md`. If an image for the commit's airlock was not published the unit keeps the airlock image already running.

**Other bridge assumptions.** Redis and the purge URLs (`BLOT_REVERSE_PROXY_URLS` is the host's private address on :8077, which a host-network unit reaches as well as the bridge did) need no change; the deploy's purge probe now runs from the unit. DNS is the host's.

**Import pin kept.** Import status lives in files under the shared tmp directory (`status.txt`, the lease, `cancelled.txt`) and Redis pub/sub, so it no longer needs one container, but the pin also keeps the heavy import work on the worker, and dropping it changes what the proxy parity test compares, which I cannot run here. Left as a follow-up with the comment corrected.

**Ops.** `check_docker_health.sh` restarts a unit but never both (blue first, and not while the other is starting or unhealthy) and not while a deploy holds the lock. The `.bashrc` helpers, `logs blue/node-a`, the data-volume scripts' default container and the `node-response-time-review` skill follow `blot-blue`. `deploy-proxy.yml` now fails with a pointer to the rollback instructions (after the cutover it would replace the units' Node with nothing); `npm run deploy-node` refuses to run. The old Node deploy code is still there, unused, for PR 7.

Tests: `proxy/deploy/tests/run.sh` covers the cutover, steady and re-run deploys, node-a/node-b/verify/airlock failures rolling back with green untouched, the env conflict check and the host health cron. `proxy-deploy-e2e.yml` has a real-Docker job doing the cutover under load, a re-run, a steady deploy and a rollback with a stand-in unit image (the real proxy image with a stub for the app and the airlock); the real app, verify-container checks and airlock are not covered there.

## Deployment plan

Label: `manual-deploy`.

1. Before merging: on the host, check `/etc/blot/secrets.env` and `/etc/blot/proxy.env` agree on any key they both set (`BLOT_HOST`, `BLOT_PURGE_TOKEN`); the deploy refuses otherwise, before touching anything. `/run/blot`, `/var/instance-ssd/tmp` and `/var/www/blot/data` already exist. The `deploy` user needs to read both env files (it already reads `secrets.env`; `proxy.env` has the ACL from `setup-deploy-user.sh`).
2. Merge, and wait for `blot-unit:<sha>` (unit-image) for the merge commit.
3. Run the **Deploy** workflow once, at a quiet time. It is the cutover; expect it to take several minutes (each unit gets up to 180s to start). Watch `docker ps`.
4. Verify: `blot-blue` and `blot-green` run `ghcr.io/blotcms/blot-unit:<sha>`, `blot-blue-airlock` and `blot-green-airlock` are healthy, `blot-container-*` and `blot-airlock` are stopped (Exited), both units show healthy. In the logs `unit=blue`/`unit=green` is on the access-log lines and `blue/node-a`, `blue/node-b` on the Node lines (`logs blue`). A blog and the dashboard load, and a sync (Dropbox or git) completes.
5. Roll back if needed: `docker start blot-airlock blot-container-yellow blot-container-green blot-container-blue`, then `scripts/deploy/units.sh --proxy-only` (see `proxy/deploy/README.md`, "Rolling back the cutover").
6. After the units have run well for a few days: `docker rm blot-container-blue blot-container-green blot-container-yellow blot-airlock`. PR 7 removes the old code and the unused workflow.
